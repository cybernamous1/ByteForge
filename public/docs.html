Documentation

This page describes what the current build actually does. Anything not listed here is not implemented.

Workspace and storage

Your project (files, folders, open tabs, SQL editor text) is stored in this browser's IndexedDB, and the Database Studio SQLite file is stored separately in the same database. Preferences (theme, font size, …) are stored in localStorage. Nothing is sent to a server. Storage is not encrypted, and browsers may evict site data under storage pressure unless persistent storage is granted (Settings → Request persistent storage). Download a project backup regularly.

The workspace is saved automatically about 0.7 seconds after changes, and when the tab is hidden or closed. If saving fails (quota, private browsing), the status bar shows NOT SAVED and a warning appears. Opening ByteForge in two tabs at once is not supported: the last save wins, and a warning is shown.

Editor

The editor is Monaco (the engine behind VS Code) with multi-file tabs, a file tree with folders, rename/move/delete, project-wide search (literal or regular expression), quick open (Ctrl/Cmd+P) and the Monaco command palette (F1). Diagnostics are syntax errors only for JavaScript/TypeScript, because npm packages and Node.js type definitions are not available to the in-browser language service. JSON, CSS and HTML use Monaco's built-in language services. Binary files (images, fonts, …) are preserved and can be downloaded but not edited.

Terminal

Before the runtime starts, the terminal is a small workspace shell. It is not a POSIX shell: there is no piping, globbing, job control or environment. Commands: help ls tree cat head tail mkdir touch rm mv cp echo grep wc node python sql run sync preview clear. They operate on the real workspace, so rm and mv change your project. echo text > file and >> are supported. Tab completes paths; arrow keys browse history.

run starts the WebContainer runtime and attaches its real jsh shell. Workspace edits are copied into the container automatically. Files created by the runtime (for example by npm) are not copied back automatically: use sync in the workspace shell, the “Pull runtime files” button, or the ⋮ menu. node_modules and .git are never copied back, and files deleted inside the runtime are not deleted from the workspace.

Preview

Static preview renders an HTML file from the workspace in a sandboxed frame. Linked stylesheets, classic <script src> files and local images are inlined. console output and errors appear in the Output tab. It refreshes as you type. Limits: type="module" scripts and ES module graphs are not inlined (use a dev server in the Node.js runtime), the frame has an opaque origin (no access to the workspace; localStorage and cookies are unavailable to it), and external resources are subject to the page's cross-origin isolation rules, so many third-party CDN resources will be blocked.

Runtime preview appears automatically when a dev server inside the Node.js runtime starts listening, and can be opened in its own tab.

Database Studio

Run any number of SQL statements (Ctrl/Cmd+Enter runs the selection, or everything when nothing is selected). Results are shown as tables (first 500 rows). You can export the database as a .sqlite file, export a portable .sql dump (schema + data), export the last result as CSV, import a .sqlite/.db file (replaces the current database after confirmation) or run a .sql script. The database is saved in IndexedDB after write statements. PostgreSQL, MySQL, DuckDB and other engines are not included in this build.

Import and export

Import: files, folders, ZIP archives (also by drag and drop). ZIP entries with unsafe paths (..) are skipped; node_modules and .git are ignored; single top-level folders are unwrapped; files above 50 MB, archives above 300 MB or 5000 files are partly skipped and reported. You are asked before existing files are overwritten. Binary files are kept as binary. SQLite files found in an import can be loaded into Database Studio.

Export: a ZIP of the project, generated locally. Environment files (.env, .env.local, …; templates such as .env.example are always included) are excluded unless you opt in and acknowledge the warning. The dialog lists every potential secret found. You can include the SQLite database. Individual files can be downloaded from the ⋮ menu.

Secret detection

Files are scanned locally as you type, on import and before export. Patterns include private key blocks, AWS access key IDs, GitHub, Slack, Stripe, Google API and sk- style keys, JSON Web Tokens, database URLs with passwords, bearer tokens and generic password/secret/token/api key assignments (placeholders such as replace_me, process.env.X and template files like .env.example are ignored). Findings appear in the Problems panel with masked values. Detection is heuristic: it can miss secrets and can flag harmless text. Values are never transmitted or modified.

Troubleshooting

  • “Runtime unavailable: not cross-origin isolated” — the host is not sending the COOP/COEP headers, or the browser is unsupported. When self-hosting, deploy with the included public/_headers (Cloudflare Pages).
  • “NOT SAVED” — browser storage is full or disabled. Download a backup, free space, and request persistent storage in Settings.
  • Preview is blank or missing styles — check the Output tab for “[preview]” notes (missing files, module scripts).
  • Runtime started but the preview does not open — the dev server must listen on a port and bind to 0.0.0.0 or localhost inside the container (vite --host 0.0.0.0).
